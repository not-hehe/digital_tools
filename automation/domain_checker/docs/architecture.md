# Устройство кода

Актуальное описание того, что есть в репозитории. Формы данных ниже сняты
с работающего кода 10.09.2026, а не написаны по памяти.

Этот документ самодостаточен: всё нужное для чтения кода есть здесь.
Подробный разбор каждого модуля и функции лежит рядом, в `code.md`.
Источник правды по формам данных - этот документ и сам код.

## Что происходит за один прогон

```
run.sh                подхватывает .env, зовёт main.py, отдаёт его код возврата
  |
  v
main.py               один прогон и выход, планировщика внутри нет
  |
  |-- sources         Excel -> список целей (отсев, дедупликация, контуры)
  |-- probe           цели -> результаты (пул потоков, по одному запросу)
  |-- alerting        результаты -> события -> текст -> Mattermost
  v
код возврата          0 прогон состоялся, 1 не состоялся, 2 ошибка в аргументах
```

Полный прогон помнит состояние между запусками и шлёт сообщение только
на смену статуса. Выборка (`--limit N`) состояние не трогает вовсе.

## Слои

Три пакета плюс два общих модуля. Деление по ответственности, а не по типу
кода: каждый слой можно читать, не зная внутренностей соседнего.

| Слой | Отвечает за | Файлы |
|---|---|---|
| `config.py` | все настройки и московское время | 1 |
| `urls.py` | нормализация адреса, отсев мусора | 1 |
| `sources/` | откуда берётся список доменов | `targets.py`, `excel_reader.py` |
| `probe/` | как проверяется домен | `checker.py`, `failures.py` |
| `alerting/` | что делать с результатом | `state.py`, `alert.py`, `notifier.py` |

Зависимости идут в одну сторону, циклов нет (проверено обходом импортов):

```
config, urls          ни от чего не зависят
sources   -> config, urls
probe     -> config, urls
alerting  -> config, probe
main.py   -> config, sources, probe, alerting
```

`urls.py` лежит наверху, а не внутри `sources/`, потому что нормализация нужна
двум слоям: списку - чтобы отсеять мусор до запроса, проверке - чтобы собрать
адрес следующего шага редиректа.

Каждый пакет отдаёт публичные имена через свой `__init__.py`, и точка входа
импортирует пакеты, а не файлы внутри них: `from modules.probe import
check_all`. Файл внутри слоя можно переименовать или разбить, не трогая
вызывающих.

## Формы данных

**Target** - одна цель проверки. Собирается в `sources`.

```python
{"url": "https://example.com", "label": "example.com", "contour": "unknown"}
```

`contour` это `internal`, `external` или `unknown`. Метка приезжает из колонки
`contour` во входном файле, колонки нет - все цели неразмеченные.

**LoadResult** - что отдаёт `load_targets`.

```python
{"targets": [Target, ...],
 "skipped": ["нет", "va-audio", "?"],        # строки, не похожие на адрес
 "counts":  {"internal": 0, "external": 0, "unknown": 366}}
```

Пустой список целей это не пустой `targets`, а исключение `EmptyTargetList`:
тихий прогон по нулю целей обнулил бы состояние и промолчал бы в канал.

**CheckResult** - что отдаёт `check_domain` по одной цели.

```python
{"url": "https://example.com", "label": "example.com", "contour": "unknown",
 "ok": False,                  # единственный признак, по которому судим
 "status_code": 500,           # None, если ответа не было вовсе
 "final_url": "https://example.com",
 "redirects": [],              # цепочка промежуточных адресов
 "elapsed_ms": 137,
 "failure_kind": None,         # заполнено, когда ответа не было: dns, tls, ...
 "failure_label": None,        # человеческая формулировка того же
 "error": None,                # текст исключения, если было
 "checked_at": datetime}       # МСК, наивное
```

`ok` считается ровно так: пришёл ответ и его код попал в 200..399. Содержимое
не разбирается.

**Состояние** - файл JSON, по записи на домен.

```python
{"version": 1,
 "updated_at": "2026-09-10T17:45:37",
 "domains": {"example.com": {"fails": 1, "down": False, "since": None}}}
```

`fails` - сколько неудачных прогонов подряд. Домен признаётся упавшим, когда
их набирается `CONFIRM_FAILS` (сейчас 2). `since` - когда признали.

**Event** - смена статуса, единственное, о чём сообщаем в канал по расписанию.

```python
{"event": "down",              # или "up"
 "label": "example.com", "url": "https://example.com",
 "since": "2026-09-10T17:45:37", "contour": "internal",
 "reason": "HTTP 500"}
```

## Решения в коде, которые неочевидны при чтении

**Редиректы проходятся вручную, шаг за шагом** (`probe/checker.py`). При
автоматическом следовании `requests` отдаёт только итоговый ответ, а
промежуточные адреса теряются - хотя именно они показывают, куда домен уводит.

**Тела страниц не скачиваются**: запрос идёт с `stream=True`, читаются только
заголовки. Нужен один код ответа, а при 288 прогонах в сутки скачанные
страницы это десятки гигабайт трафика впустую.

**Дедупликация живёт только в `sources/targets.py`.** Читалка Excel умеет
и сама, но два места, где домен может пропасть, это два места, куда придётся
смотреть, когда он однажды пропадёт зря.

**`ConnectTimeout` проверяется раньше `ConnectionError`**
(`probe/failures.py`). Он наследуется от обоих, и при обратном порядке все
таймауты схлопнулись бы в "соединение отвергнуто", а целый класс отказов
пропал бы из отчёта.

**Предохранители стоят на обоих путях отправки** (`alerting/alert.py`). Если
разом легла большая доля списка или целиком один контур, в канал уходит одна
строка вместо перечня сотен адресов. Восстановление проверяется наравне
с падением: вернувшийся маршрут даёт такой же поток строк, что и отказавший.
Ниже `GUARD_MIN_ITEMS` предохранители молчат - перечень из трёх адресов
полезнее строки "упало 3 из 4".

**Выборка не трогает состояние** (`main.py`). Прогон по пяти адресам обновил
бы записи только этих пяти, а остальные 361 домена выпали бы из состояния и
на следующем полном прогоне пришли бы как новые.

**Несохранённое состояние роняет прогон, а нечитаемое - нет.** Файл, который
не удалось прочитать, это первый запуск. Файл, который не удалось записать,
означает, что счётчик отказов начнёт следующий прогон с нуля и до порога
не дойдёт никогда: канал замолчит навсегда, и это неотличимо от исправной
работы. Сообщение при этом успевает уйти - события уже посчитаны.

**Heartbeat рождается из боевого прогона**, а не из отдельной строки
расписания: иначе он подтверждал бы работу этой строки, а не работу чекера.
Отметка `last_heartbeat` живёт в состоянии и переносится через `apply_results` -
без переноса она терялась бы каждый прогон, и признак жизни уходил бы в канал
каждые пять минут.

**О непрошедшем прогоне сообщает обёртка, а не сам прогон** (`run.sh` через
`tools/notify.py`). Упавший прогон не может рассказать о собственном падении,
а то и не доходит до импорта.

**Отправитель передаётся параметром** (`alerting/alert.send`). Иначе
невозможно проверить тестом, что при здоровых доменах в канал ничего
не уходит: нечем посчитать отсутствие вызовов.

## Где что менять

| Задача | Куда идти |
|---|---|
| Другой источник списка вместо Excel | `sources/`, форма LoadResult та же |
| Другой признак живого домена | `probe/checker.py` + границы в `config.py` |
| Новый вид отказа в отчёте | `probe/failures.py` |
| Другой канал вместо Mattermost | `alerting/notifier.py` |
| Тексты сообщений, пороги предохранителей | `alerting/alert.py`, `config.py` |
| Правила подтверждения падения | `alerting/state.py`, `CONFIRM_FAILS` |
| Хранилище состояния вместо файла | `alerting/state.py`: `load_state`, `save_state` |

## Тесты

```bash
venv/bin/python tests/test_logic.py       # 41 тест, сеть не нужна, ~1 с
venv/bin/python tests/test_e2e_local.py   # 6 проверок на 127.0.0.1, ~5 с
```

Раннер сам находит функции с префиксом `test_` - ручного списка нет
намеренно: тест, забытый в списке, молча не выполняется, а раннер при этом
рапортует об успехе.

Логика покрыта по границам: правило `ok` на 199/200/399/400/None, все виды
отказов, нормализация и отсев адресов, загрузчик с дедупликацией и контурами,
пять сценариев подтверждения падения, оба предохранителя в обе стороны,
отсутствие адреса вебхука в коде. E2E поднимает `http.server` на свободных
портах и проверяет на живом сокете 200, 404, 503, цепочку редиректов,
закрытый порт и параллельность пула.
