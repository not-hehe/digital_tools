# domain_checker

Следит за доступностью списка доменов и пишет в Mattermost, когда что-то легло.

## Задача

Узнать, что сайт перестал отвечать, раньше, чем об этом сообщат пользователи.
Важен только факт: домен жив или мёртв. Причина, место и подробности отказа
роли не играют, разбираться в них будут люди.

Проверка идёт раз в пять минут. Это накладывает два ограничения, которые
определили почти все решения в проекте.

**Прогон обязан укладываться в окно.** Если проверка списка занимает больше
пяти минут, запуски начинают наползать друг на друга. При таймауте 15 секунд
и десяти потоках худший случай, когда легла вся сеть, занимал бы девять минут.
Сейчас 366 адресов проверяются за 14.5 секунды, худший случай около двадцати
секунд.

**Канал не должен зашуметь.** Один упавший домен при таком интервале дал бы
288 сообщений в сутки. Поэтому сообщение уходит только в момент смены
состояния: домен упал или домен поднялся.

## Как работает

Список адресов читается из Excel. Загрузчик спрятан за интерфейсом, так что
источник можно поменять, не трогая ни проверки, ни оповещение.

Дальше пул потоков обходит адреса. По каждому снимается код ответа, цепочка
редиректов и время отклика. Домен считается живым, если сервер ответил кодом
от 200 до 399 включительно. Всё остальное, включая отсутствие ответа, это
падение.

Редиректы проходятся вручную, шаг за шагом. При автоматическом следовании
requests отдаёт только итоговый ответ, а промежуточные адреса теряются, хотя
именно они показывают, куда домен уводит.

Тела страниц не скачиваются: запрос идёт с stream=True, читаются только
заголовки. Нужен один код ответа, а при 288 прогонах в сутки скачанные
страницы это десятки гигабайт трафика впустую.

Падение подтверждается двумя неудачными прогонами подряд. Одиночное сетевое
моргание не должно поднимать тревогу, цена подтверждения это пять минут
задержки.

## Почему Python, а не что-то быстрее

Вопрос возникал всерьёз, и ответ дал замер, а не рассуждение.

Из 14.5 секунды прогона на процессор приходится около 3 секунд, остальное
процесс просто ждёт сокет. Причём большая часть этих трёх секунд это OpenSSL
на TLS-рукопожатиях, то есть уже нативный код.

Переписывание на C++ обнулило бы пару секунд из четырнадцати ценой собственной
реализации TLS, редиректов, DNS и punycode. Переход на asyncio дал бы около
шести секунд вместо четырнадцати при бюджете в триста, то есть запас вырос бы
с двадцатикратного до сорокакратного и не купил бы ничего.

Возвращаться к вопросу имеет смысл, если список перевалит за пару тысяч
адресов или интервал станет короче тридцати секунд.

## Запуск

```bash
cd automation/domain_checker
python3 -m venv venv
venv/bin/pip install -r requirements.txt

venv/bin/python main.py 12        # проверить первые 12 адресов
```

Синтаксис держится совместимым с Python 3.9: версия на сервере Airflow заранее
не известна, а совместимость вниз дешевле, чем разбирательство на месте.

Входной файл: data/input_urls.xlsx, колонка url. Рядом лежит
data/input_urls.example.xlsx с обезличенными адресами, на нём можно запустить
сразу после установки.

## Настройки

Всё в modules/config.py, секреты читаются из окружения. Шаблон переменных
в .env.example.

| Параметр | Значение | Смысл |
|---|---|---|
| MAX_WORKERS | 100 | размер пула потоков |
| REQUEST_TIMEOUT | 5 | секунд на запрос |
| MAX_REDIRECTS | 5 | глубже считается зацикливанием |
| HEALTHY_MIN, HEALTHY_MAX | 200, 400 | границы кода живого домена |
| TRUST_ENV | выкл | брать ли прокси из переменных окружения |
| DC_MATTERMOST_WEBHOOK | из окружения | пусто, значит не отправлять |

Про TRUST_ENV стоит знать отдельно. По умолчанию прокси из окружения
игнорируется. Если на сервере выход в интернет идёт через прокси, с таким
значением все внешние домены дадут ложные отказы. Проверяется первым прогоном
на месте.

## Состояние

Работает: чтение списка, параллельный обход, разбор ответа и отказа,
построение текста сообщения.

В работе: отправка в Mattermost и хранение состояния между запусками, без
которого нельзя определить смену статуса.

Не делается сознательно: проверка сертификатов, срок регистрации домена,
разбор содержимого страницы. Домен, отвечающий заглушкой хостера с кодом 200,
считается живым.
